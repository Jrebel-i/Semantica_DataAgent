# 修正覆盖层迁入源目录 Git 管理，纠错与演化共用提案管线与项目级双开关

Status: accepted

原架构遵循 [0004](0004-corrections-via-approved-proposals.md) 与 [0007](0007-ossie-semantic-interchange.md) 将**修正覆盖层**存在应用数据库 `metadata_overrides` 表中且仅支持表/字段单段 `comment` 文本，无法承载外键关系、同义词、使用约束与已审定指标，也不在 Git 管理的**源目录**中；同时 `DTB 拉取为 Ossie` 定时重拉会覆盖拉取文件，而一律强制管理员审批在缺乏专职审批人力的项目中会阻塞纠错落地。因此第八期作出两项核心决策：

1. **修正覆盖层迁入源目录 Git 管理并结构化升级**：将修正覆盖层迁移至项目**源目录**下的受控文件 `overrides/semantic_overrides.yaml`（纳入 Git 提交历史，并兼容迁移既有数据库 `metadata_overrides` 记录），扩展支持表/字段说明、同义词、AI 使用约束、显式外键关系（`RELATES_TO`）与已审定指标；构建时在 `dtb`、`ossie` 等基础**源适配器**产出之上确定性叠加，确保不被后续定时拉取覆盖，使源目录真正成为唯一权威来源。提交新**纠错提案**时严格校验物理表/列存在性与语法（不通过返回 `422`）；后续上游数仓表结构变更导致已有覆盖目标消失时，构建软跳过失效条目以保证整库构建成功，同时记录显式过期覆盖告警（`stale_overrides`）供管理员处理。
2. **统一纠错提案管线与项目级双审核开关**：提问者主动纠错、MCP 提案与自主演化产出统一收敛至同一条**纠错提案**生命周期，复用统一的 Git 提交、自动增量构建触发与安全 `git revert` 反向提交回滚机制（发生冲突时安全中止并返回 `409`）。项目设置独立提供「主动纠错需审批」（`correction_require_review`）与「自主演化需审批」（`evolution_require_review`）两项开关，新建与存量项目默认均为开启；管理员关闭某项开关后，对应来源的提案在通过确定性与/或评测门禁后即可自动写回源目录并增量生效，但项目开关切换与事后回滚权限仍严格保留给项目管理员与系统管理员。

## Considered Options

- **仅升级应用数据库 `metadata_overrides` 表并新增 JSON 列**：不纳入源目录 Git 提交历史，无法实现统一 `git revert` 与重建自包含，违背“源目录是唯一权威来源”原则，故放弃。
- **为自主演化另建独立审批流与存储结构**：会导致知识改动来源分散、前端审批重复且回滚语义割裂，不如共用**纠错提案**管线并以来源与门禁报告字段区分。

## Consequences

- `table_stage` 与 `ossie_source` 构建流程须优先读取源目录 `overrides/semantic_overrides.yaml`，并对存量 `metadata_overrides` 表执行幂等迁移兼容；所有生效的纠错提案（包括元数据覆盖）统一触发增量构建。
- 前端与知识问答页面允许对 `generated=true` 的 Ossie 派生**知识文档**发起纠错，由后端自动编译路由到对应物理对象的修正覆盖层而非拒绝请求。
