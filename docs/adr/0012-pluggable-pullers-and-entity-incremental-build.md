# 项目级插件化数据源拉取器、任务副产物保留与实体级增量构建

Status: accepted

第六期 [0008](0008-dtb-to-ossie-pipeline.md) 打通了 DTB 到 Apache Ossie 的单轨尝试，但仍遗留五项结构性痛点：旧版原始 `dtb` 导出轨与 `ossie` 轨并存互斥；拉取器与查询执行器硬编码且仅限默认项目配置；转 Ossie 过程中丢弃原始**数仓任务**导致 `read_task_sql` 与多层/字段级**上游依赖**不可用；定时调度仅支持相对秒数间隔且缺乏无变更跳过与骤降熔断；增量构建按整文件哈希触发并原地先删后写，在单文件大 Ossie 场景下既慢又不安全。第十期对此做整体架构收口，取代 [0008](0008-dtb-to-ossie-pipeline.md)：

1. **统一单轨与项目级多实例数据源拉取器协议**：
   - 数仓型项目的外部接入彻底收口为「**数据源拉取器**（Python entry-point 插件）→ 产出标准 Apache Ossie 语义模型及配套规范副产物落入**源目录** → 统一由**源适配器**构建」，新版本完成后直接下线旧版原始 `dtb` 导出与拉取双轨。
   - 拉取器配置（连接参数、过滤范围、定时规则、加密服务令牌）全面下沉到项目级，每个**数仓型项目**可挂载 `0..N` 个拉取器实例，前端按插件声明的 `parameters_schema` 自动渲染配置表单。DTB 作为首个内置参考插件重构接入（保留与离线 CLI 复用的确定性转换核心）。
   - 每个拉取器实例严格隔离在各自命名子目录（Ossie 模型置于 `ossie/<instance_id>/`，配套产物置于 `pulls/<instance_id>/`），绝不修改人工维护的**知识文档**与**修正覆盖层**；构建时按「拉取产物 → 叠加修正覆盖层」合并，上游删表/改列导致的失效覆盖跳过并显著告警、不阻断定时更新。
   - 多实例共存支持按实例配置独立 `catalog` 前缀与任务命名空间；合并为**规范数据模型**时若仍出现重复的物理表或任务标识，构建快速失败并明确指出冲突的两个拉取器实例，禁止静默覆盖。
   - **文档型项目**维持现有多源可扩展边界，由各源适配器声明支持的 `project_types`，不强行限定仅 Markdown。
2. **原生单文件 Ossie + 配套数仓任务与混合维度值**：
   - 每个拉取器实例产出一份 100% 符合原生 Apache Ossie 规范的模型 YAML（完整内嵌跨表/跨库**外键关系**），并同步产出配套规范 `tasks.json` 以保留 `SDATask`、`read_task_sql` 及多层/字段级**上游依赖**。
   - 保留**维度值**分层混合策略：低基数字段原样内联进 Ossie 字段说明，高基数字段在说明保留少量样例并将完整码表落盘至 `dimension_values.json` 进入 Neo4j 维度索引（不进 Milvus），并将低基数阈值、抽样数量与单表行数上限暴露为插件可配参数。
3. **每日固定时刻调度与防误删容错机制**：
   - 定时调度从相对秒数升级为按拉取器实例配置的每日固定时刻（`HH:MM` / Cron + 时区），服务重启不漂移且保持 fork 安全。
   - 每次拉取落地前执行三项保护：（a）产物与该实例上次源目录内容无实质差异时跳过提交与构建；（b）表数量为 0 或相比上次有效快照骤降超过可配阈值（默认 50%）时触发熔断中止落盘并告警，需人工确认强制拉取；（c）单张维表等局部拉取失败时沿用该项上次快照并记录局部告警，避免局部抖动清空维度索引。
4. **规范实体级哈希精确增量 + 预计算向量 + 全量新建代兜底**：
   - 增量构建由“整文件哈希 diff”升级为“**规范数据模型**实体内容哈希 diff”（按表+字段单元、数仓任务、维表、知识文档、外键关系逐项比对），每天只更新真正变动的少数实体。
   - 增量修改存储前先完成新增/变更实体的 Embedding 计算（优先命中本地 SQLite 缓存）再执行 Neo4j 与 Milvus 替换，最小化原地增量窗口风险；在首次构建、配置/插件变更、单次变更比例超过可配阈值（默认 20%）或增量写入失败时，自动退化为全量重建新**知识代**并原子切换兜底。
5. **项目级查询执行器解耦与凭据分层**：
   - **查询执行器**（如 DTB 执行器）同样下沉为项目级可选插件，与**数据源拉取器**解耦（允许数仓型项目仅配置拉取器做**知识问答**而不开放**取数**）。
   - 严格保持凭据分层：无人值守定时拉取使用项目级服务令牌，在线交互式**取数**与**数据探活**继续绑定提问者个人令牌以保障数据权限隔离与审计归属。

## Considered Options

- **将 Ossie 按单表拆为 `ossie/<db>/<table>.yaml` 以继续沿用文件级增量**：Apache Ossie 规范要求 `relationships` 引用的 `from`/`to` dataset 位于同一语义模型文件内，按单表拆分会迫使所有跨表/跨库外键脱离原生 Ossie 规范，同时在源目录制造上千个 YAML 文件与衍生文档；改用实体级内容哈希 diff 即可在不破坏原生 Ossie 格式的前提下获得同等表级增量速度，故放弃。
- **每日定时变更一律走全量新建知识代重建**：虽具备最高原子性，但在 ~1,800 张表、近 5 万字段规模下每日仅变动数张表却全量重写图与向量存储耗时与 I/O 成本过高；采用“预计算向量 + 实体级精确增量”配合“超阈值/失败自动全量新建代兜底”兼顾秒级日常更新与异常自愈，故采用混合方案。
- **支持网页低代码脚本编辑器定义新数据源**：显著引入安全执行沙箱与调试维护复杂度，当前团队以工程插件扩展为主，采用标准 Python entry-point 协议 + JSON Schema 自动表单即可满足插件化目标，故放弃。
- **拉取器与查询执行器共用同一套凭据**：复用项目服务令牌执行个人取数会击穿数仓表/行级权限与审计，复用个人令牌跑后台定时拉取则会因个人过期导致夜间中断，故明确保持分层隔离。

## Consequences

- 旧版 `dtb` 源适配器、`dtb` 原始导出拉取器以及 `("dtb", "ossie")` 硬编码互斥逻辑将在第十期整体下线清理；需通过数据库迁移将现有默认项目的 `puller/ossie` 或 `puller/dtb` 配置平滑迁入新的项目级拉取器实例表。
- `builds` 记录将新增规范实体哈希快照以驱动跨构建实体级 diff；增量构建中的图关系对齐（`reconcile`）需改为局部增量对齐，避免每次微调触发全图扫描。
- 源目录中同一项目跨拉取器实例出现重复物理表或任务标识将被视为硬错误拦截，管理员需通过实例级 `catalog` 或命名空间隔离，而非依赖合并覆盖。
