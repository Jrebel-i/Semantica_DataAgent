# Ingestion plugins

Install Python distributions in the application environment. Source adapters register a no-argument class in the `semantica_dataagent.source_adapters` entry point group; task parsers use `semantica_dataagent.task_parsers`. Each class exposes `id`, `version`, `display_name`, and a JSON Schema object `parameters_schema`. IDs must be unique within their group. The built-in `canonical` and `markdown` adapters and the built-in `sql` parser are enabled by default; every other plugin, including the built-in `dtb` adapter and parser, starts disabled.

A source adapter implements `read(directory: Path, parameters: dict) -> ReadResult`, returning canonical `Record` objects, source hashes and optional non-negative integer statistics (see `canonical.py`). Build statistics merge adapter statistics with the plugin ID as a prefix, so an adapter that cannot read a value can report it as unknown instead of silently emitting an empty value. A task parser exposes `task_types` and implements `parse(task: Record, parameters: dict) -> ParseResult`. Dispatch selects the first enabled parser whose `task_types` contains the canonical task's `type`; absent a match, it returns `unsupported`. Parser results contain `reads`, `writes`, `status`, and an optional `reason`. Canonical tasks may carry an optional `parameters` object for parser-specific task configuration; core code does not interpret it.

The built-in `dtb` adapter reads a dtb export snapshot (`manifest.json`, `任务信息.json`, `表信息.xlsx`) plus dimension-table rows. Its parameters are `snapshot_path` (relative directory holding versioned snapshots), `snapshot` (exact version; overrides `latest`), `latest` (default true), `dimensions_path` (relative dimension root), `dimension_tables` (optional allowlist) and `dimension_row_limit` (default 50000 rows per table). Missing values, unreadable `task_conf` values, unresolved upstream task IDs, truncated dimension tables and malformed rows are reported as `dtb_*` build counts; structural file errors fail the build instead of yielding an empty result. The built-in `dtb` task parser handles `shell` (Livy `submit_sql_and_wait` and `beeline -e` SQL extraction, recursive shell-variable expansion, then a `shell_basic` regex fallback) and `merge_onself` (target table from `params.table` in the task configuration, with the self edge suppressed). Spark SQL tasks use the generic `sql` parser.

Administrators use `/plugins` to configure plugins and database/task include and exclude wildcard patterns. Exclusions take precedence, empty inclusion lists match everything, and `tmp` and `test` are excluded by default. Changes apply to the next build. Build statistics include the number of filtered canonical records.

Build stages are listed in `semantica_dataagent.stages.STAGES`; each receives records, generation, and a `StorageHandles` instance and returns `StageResult` counts and errors. The build initializes and clears the generation once and creates the shared Milvus collection before running stages, then loads it after all stages succeed. Stages use `storage.execute()` to append `SDAEntity` graph nodes tagged with the generation and `storage.add_vectors(ids, texts, metadata)` to append vectors with a nonempty `scope`; the handle embeds texts and sets the generation. Stages must not clear graph data or create, drop, or load the collection. Exceptions and reported errors fail the build. Table REST and MCP endpoints are in `table_api.py`.

## Real-data sample and lineage comparison

The real-data helpers are standalone scripts; their output goes to `data/`, which is gitignored. `scripts/dtb_sample.py` starts from the `quick_base/air/字典` table documents, follows the facts `lineage_edges.jsonl` upward for two levels, includes the producing tasks and their direct upstream tasks, copies related dimension tables (row cap), and writes a dtb snapshot plus a Markdown knowledge directory that the `dtb` and `markdown` adapters read directly. Dictionary and business documents stay complete; metric documents keep an initial character window because their chunk count is the embedding budget bottleneck. The default output needs about 5,300 vectors (`data/dtb-sample/dtb/manifest.json` records the exact counts and the 2–3 texts/s estimate); `--max-vectors` rejects a sample that exceeds the budget.

`scripts/dtb_lineage_compare.py` parses the full raw snapshot offline and compares the resulting table edges with `warehouse/facts/_catalog/lineage_edges.jsonl`. It normalizes table names to lower-case `database.table`, drops self edges, reports overall and per-task-type recall/precision, splits recall by the facts evidence sources, and writes `data/lineage-compare.md` and `data/lineage-compare.json` with missing and extra examples.

`scripts/verify_sample_build.py` runs the normal build against the isolated test Neo4j/Milvus and the local embedding service. It creates a unique knowledge generation, compares the build counts with the sample manifest, records graph and embedding statistics, and removes that generation's graph nodes and Milvus collection in `finally`. It requires `NEO4J_PASSWORD` (the test Secret's value after `neo4j/`) in the environment and never writes it to disk.
