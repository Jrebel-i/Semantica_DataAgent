# Ingestion, puller, and executor plugins

Install Python distributions in the application environment. Source adapters register a no-argument class in `semantica_dataagent.source_adapters`; task parsers use `semantica_dataagent.task_parsers`; data source pullers use `semantica_dataagent.pullers`; query executors use `semantica_dataagent.executors`. Each source adapter declares `project_types`, a tuple of project types it can read (`warehouse`, `document`): the built-in `canonical` and `ossie` adapters support only `warehouse`, and `markdown` supports both. Legacy third-party adapters without the attribute are treated as `warehouse` only. Each class exposes `id`, `version`, `display_name`, and a JSON Schema object `parameters_schema`. IDs must be unique within their group. The built-in `canonical` and `markdown` adapters and the built-in `sql` parser are enabled by default; `ossie` and `dtb` task parser start disabled unless configured per project.

A source adapter implements `read(directory: Path, parameters: dict) -> ReadResult`, returning canonical `Record` objects, source hashes and optional non-negative integer statistics (see `canonical.py`). Each record must set `source_file` to a source-directory-relative path present in its `ReadResult.hashes`; adapters must update the hash whenever that file changes. Builds reject records without provenance. For derived records, `source_key` identifies a deterministic derived hash and `source_files` lists the actual inputs. Build statistics merge adapter statistics with the plugin ID as a prefix, so an adapter that cannot read a value can report it as unknown instead of silently emitting an empty value. A task parser exposes `task_types` and implements `parse(task: Record, parameters: dict) -> ParseResult`. Dispatch selects the first enabled parser whose `task_types` contains the canonical task's `type`; absent a match, it returns `unsupported`. Parser results contain `reads`, `writes`, `status`, and an optional `reason`. Canonical tasks may carry an optional `parameters` object for parser-specific task configuration; core code does not interpret it.

The built-in `dtb` task parser (`dtb_tasks.DtbTaskParser`) handles `shell` (Livy `submit_sql_and_wait` and `beeline -e` SQL extraction, recursive shell-variable expansion, then a `shell_basic` regex fallback) and `merge_onself` (target table from `params.table` in the task configuration, with the self edge suppressed). Spark SQL tasks use the generic `sql` parser.

The built-in `ossie` adapter (`ossie_source.OssieAdapter`) reads Apache Ossie YAML (`.yaml`/`.yml`) and JSON (`.json`) semantic model files for `warehouse` projects (including per-puller-instance subdirectories `ossie/<instance_id>/`). Its parameters are `path` (source-relative directory, default `"ossie"`; missing directory yields an empty `ReadResult`), `category` (knowledge category for derived Markdown documents, default `"ossie"`), and `strip_catalog` (boolean, default `false`; strips the leading catalog segment from three-part `catalog.database.table` dataset sources). It rejects duplicate JSON/YAML keys (preserving YAML anchor merges), unwraps legacy `0.1` `semantic_model` envelopes, normalizes `0.1`/`0.2` versions and `custom_extensions` (decoding JSON-string `data` objects) to the bundled official `0.3.0.dev0` JSON Schema (`schemas/ossie/ossie-schema.json`), rejects duplicate physical tables across puller instances, and performs a three-way split:
1. **Physical tables and columns** -> canonical `table` and `field` records (single-column expressions in `OSSIE_SQL_2026`, `ANSI_SQL`, or first dialect parsed via `sqlglot`; merges shared physical tables within an instance/root while failing on conflicting types, `partition` flags, or cross-instance duplicates; restores `partition` and `raw_type` from `nonportable_extensions` with `vendor_name="SEMANTICA_DATAAGENT"`).
2. **Explicit relationships** -> canonical `relationship` records after resolving dataset logical field names back to physical column names (relationships referencing calculated fields are skipped, counted in `ossie_skipped_calculated_relationships`, and documented in the derived Markdown doc).
3. **Derived documentation** -> `generated=true` `<model>.md` documents and `index.md` under `category`, listing full physical table names so `HAS_DOCUMENT` links connect tables to metrics, calculated expressions, AI context, and relationship notes.

Coexistence with `canonical`: `OssieAdapter.owned_paths(parameters)` declares its `path` directory, and `knowledge.read_sources` excludes enabled sibling adapters' owned paths when invoking `canonical` (`canonical.exclude_directories`), preventing `CanonicalAdapter` from rejecting Ossie `.json`/`.yaml` model files while still catching stray unknown JSON files elsewhere in the source directory. Puller instance sidecars (`pulls/<instance_id>/tasks.json` and `pulls/<instance_id>/dimension_values.json`) use standard canonical JSON schemas and are read by `CanonicalAdapter`. Category path collisions between `ossie` and `markdown` are rejected by `knowledge.validate_records`.

## Data source pullers and project instances

A data source puller implements `PullerPlugin` (`plugins.py`): exposing `id`, `version`, `display_name`, `parameters_schema` (secret fields marked with `"format": "password"` or `"x-secret": true`), and `pull(context: PullContext) -> PullArtifact`. `PullContext` supplies `project_id`, `instance_id`, public `parameters`, decrypted `secrets`, and optional `catalog_prefix` / `task_namespace`. `PullArtifact` carries `ossie_models: dict[str, bytes]`, canonical `tasks: list[dict]`, canonical `dimension_values: list[dict]`, `table_count`, `task_count`, `stats`, and partial `failures: list[PullItemFailure]`.

The built-in `dtb` puller (`dtb_ossie.DtbPluginPuller`, display name `"DTB"`) transforms remote DTB metadata, task SQL, and dimension rows directly into a validated Apache Ossie `0.3.0.dev0` YAML model plus canonical `tasks` and high-cardinality `dimension_values` (columns with distinct count `<= low_cardinality_limit`, default `20`, are inlined directly in Ossie field instructions; columns above the limit retain `sample_limit`, default `5`, samples and emit full rows up to `dimension_row_limit`, default `50000`, into `dimension_values`). The offline CLI subcommand `semantica-dataagent convert-dtb-ossie` runs the same deterministic converter (`convert_dtb_to_ossie`) on a local DTB export snapshot (`dtb_snapshot.DtbSnapshotReader`), accepting `--source-dir`, `--output-dir`, `--snapshot-path`, `--snapshot`, `--dimensions-path`, `--dimension-row-limit`, `--ossie-path`, `--model-name`, `--format`, `--low-cardinality-limit`, `--sample-limit`, and `--database`.

Warehouse projects can mount `0..N` puller instances via `/api/v1/projects/{project_id}/pull-instances` and trigger pulls via `POST /api/v1/projects/{project_id}/pull-instances/{instance_id}/pull`. Each instance is isolated into `ossie/<instance_id>/` and `pulls/<instance_id>/` without touching manual Markdown docs, top-level Ossie models, sibling instances, or `overrides/semantic_overrides.yaml`. Scheduled pulls run via `PullInstanceScheduler` using per-instance `schedule_cron` (`HH:MM` or 5-field cron) and `timezone` (default `Asia/Shanghai`). Before writing or queueing a build, `run_instance_pull` enforces: (a) byte-for-byte no-op skip (`skipped_reason="no_changes"`, no empty commit or build), (b) table-drop circuit breaker (`table_count == 0` or drop ratio `> drop_threshold` -> `status="blocked"`, bypassable with `{"force": true}`), and (c) partial `dimension_table` failure carry-forward from prior `pulls/<instance_id>/dimension_values.json` with recorded `warnings`. When source files change, a `"full"` build is queued if the project has no prior successful full build, otherwise an `"incremental"` entity-level build is queued.

## Project-level query executors

Query executors implement `ExecutorPlugin` (`bind(parameters, token) -> QueryExecutor`) and are configured independently of pullers via `GET/PUT /api/v1/projects/{project_id}/executors` (at most one enabled per warehouse project; disabled/incompatible on document projects). Online SQL execution and discovery data probing always bind the caller's personal credential rather than unattended puller service secrets.

`GET /api/v1/plugins` includes `project_types` for source adapters. Builds only run source adapters compatible with the project's immutable type, even when a global plugin configuration enables an incompatible adapter; for example, a document project never runs `ossie` or `canonical`. `project_types.ensure_adapter_compatible(project_type, adapter_id)` is the validation entry point for per-project adapter configuration (#187).

Administrators use `/plugins` to configure plugins and database/task include and exclude wildcard patterns. Exclusions take precedence, empty inclusion lists match everything, and `tmp` and `test` are excluded by default. Changes apply to the next build. Build statistics include the number of filtered canonical records.

Build stages are listed in `semantica_dataagent.stages.STAGES`; each receives records, generation, and a `StorageHandles` instance and returns `StageResult` counts and errors. Full rebuilds write to a new generation and atomically switch the pointer; incremental builds compute entity-level content hashes (`tables`, `fields`, `tasks`, `dimension_values`, `documents`, `relationships`), precompute embeddings before storage writes, and automatically fall back to a full new-generation rebuild (`fallback_reason`) when first-time, config/plugin changes, `>20%` change ratio, or incremental write failures occur. Stages must not clear graph data or create, drop, or load the collection outside stage contracts. Exceptions and reported errors fail the build. Table REST and MCP endpoints are in `table_api.py`.

## Real-data sample and lineage comparison

The real-data helpers are standalone scripts; their output goes to `data/`, which is gitignored. `scripts/dtb_sample.py` starts from the `quick_base/air/字典` table documents, follows the facts `lineage_edges.jsonl` upward for two levels, includes the producing tasks and their direct upstream tasks, copies related dimension tables (row cap), and writes a dtb snapshot plus a Markdown knowledge directory that the `dtb` and `markdown` adapters read directly. Dictionary, metric, and business documents are copied in full by default; the optional `--metric-char-limit` remains available for smaller ad-hoc samples. Markdown chunks larger than the 900-character limit (for example a table row containing a long `IN (...)` list) are split further so the embedding service never receives an oversized chunk. The default output needs about 8,388 vectors (`data/dtb-sample/dtb/manifest.json` records the exact counts and the 2/2.5/3 texts/s estimates); `--max-vectors` rejects a sample that exceeds the 8,500-vector budget. The output path is resolved and must be under this repository's `data/` directory, and an existing output is only replaced when its `dtb/manifest.json` has the script's `generator` marker.

`scripts/dtb_lineage_compare.py` parses the full raw snapshot offline and compares the resulting table edges with `warehouse/facts/_catalog/lineage_edges.jsonl`. It normalizes table names to lower-case `database.table`, drops self edges, reports overall and per-task-type recall/precision, splits recall by the facts evidence sources, and writes `data/lineage-compare.md` and `data/lineage-compare.json` with missing and extra examples.

`scripts/verify_sample_build.py` runs the normal build against the isolated test Neo4j/Milvus and the local embedding service. It creates a unique knowledge generation, compares the build counts with the sample manifest, records graph and embedding statistics, and removes that generation's graph nodes and Milvus collection in `finally`. Its SQLite settings database is marked with an application id; an existing file without that marker is never deleted. It requires `NEO4J_PASSWORD` (the test Secret's value after `neo4j/`) in the environment and never writes it to disk.
